Flow 進階與熱流

Compose UI 教學第 5 章示範了怎麼在畫面上收集 Flow。這一章看 Flow 本身：生產與消費速度不一致時怎麼辦、多條 Flow 怎麼合併，以及 Repository 與 ViewModel 最常用的 StateFlow。

背壓：生產比消費快的時候

說明

Flow 預設是循序的：emit() 會等收集端處理完這一筆才返回。所以感測器每 100ms 一筆、畫面處理一筆要 300ms 時，生產端會被拖慢到和消費端一樣，這就是 Flow 內建的背壓。如果這不是你要的，有三種調整方式：

寫法行為適合
collect（預設）生產端等消費端，一筆都不丟每一筆都重要，而且順序執行沒問題
buffer()生產端在另一個協程繼續跑，資料先排隊，一筆都不丟生產與消費都花時間，想讓兩邊同時進行
conflate()消費端忙的時候只保留最新一筆，中間的直接丟掉只在乎最新狀態，例如位置、進度
collectLatest新資料來時，取消還沒處理完的那一筆，改處理新的舊結果已經沒用，例如搜尋、重新整理

combine 與 zip：合併多條 Flow

說明

畫面狀態常常來自好幾個來源，例如使用者資料、設定、網路狀態。兩個常見的合併方式：

  • combine：任一邊有新值，就拿雙方的最新值重算一次（兩邊都至少要有一個值才開始）。ViewModel 組合 UI 狀態幾乎都用它。
  • zip：一對一配對，第 1 筆配第 1 筆、第 2 筆配第 2 筆；快的那邊要等慢的，較短的那條結束時整個結束。

範例的報價每 300ms 一筆、匯率每 700ms 一筆。combine 在匯率還沒更新時，會用舊匯率搭配新報價；zip 一次只向兩邊各要一筆，所以報價被匯率拖慢（p2 要等到約 1000ms 才產生）；配完兩對後匯率結束，zip 也跟著結束，p3 之後根本沒有產生。

flatMapLatest：如果是「依照 A 的值，切換去收集另一條 Flow」，例如依搜尋字串查詢、依選中的帳號讀資料，用 queryFlow.flatMapLatest { q -> repo.search(q) }。新的值一到就取消上一條，和 collectLatest 是同一個概念。

熱流：StateFlow 與 stateIn

說明

用 flow { } 建立的是冷流：沒人收集就不執行，每個收集者各自執行一份。兩個畫面同時收集，就會連兩次 WebSocket。熱流則獨立於收集者存在，所有人共用同一份資料：

  • StateFlow：永遠有一個目前值，新的收集者立刻拿到它；相同的值不會重複送出。用來表示「狀態」。
  • SharedFlow：可以設定重播幾筆（replay），沒有「目前值」的概念。用來廣播「事件」。

stateIn / shareIn 把冷流變成熱流，started 參數決定上游什麼時候開始與停止：

  • Eagerly：立刻開始，永不停止。
  • Lazily：第一個收集者出現時開始，之後永不停止。
  • WhileSubscribed(5000)：有收集者時執行，最後一個離開後再等 5 秒才停止。Android 官方建議的預設值，那 5 秒剛好讓畫面旋轉時不必重新連線。範例為了好觀察改成 2 秒。

一次性事件：導頁、Snackbar 這類「只該處理一次」的事件，不要放進 StateFlow（畫面重建時會再收到一次）。可以用 Channel(Channel.BUFFERED) 搭配 receiveAsFlow()，或者照 Android 官方目前的建議，把它也建模成狀態，處理完再由 UI 回報清除。
