Coroutine 與其他非同步方案

網路請求、計時器、感測器、資料庫查詢……UI 一定會碰到非同步工作。Compose 的狀態系統和 Kotlin Coroutine 是一起設計的，所以 Coroutine 與 Flow 是首選；但既有專案裡的 callback、LiveData、RxJava 也都有對應的接法。

本章聚焦在協程和畫面的整合。協程本身的取消、例外傳遞、Flow 進階與測試，請看延伸閱讀「Coroutine 邏輯層實戰」。

LaunchedEffect：跟著組合啟動的協程

說明

先講一個 Compose 的核心規則：Composable 函式只負責「依狀態描述畫面」，不應該有副作用（side effect），也就是送網路請求、啟動計時器、寫入資料這類對外部世界造成影響的事。原因是 Composable 可能每一幀都重新執行、可能被跳過、也可能執行到一半被放棄；直接在裡面呼叫 api.search(query)，可能送出十幾次，也可能一次都沒送。

Compose 提供一組 Effect API 來安全地處理副作用，LaunchedEffect 是最常用的一個：它在進入組合時啟動一個協程，離開組合時自動取消。

關鍵在 key：key 改變時，舊的協程會被取消、再用新的值重新啟動。下面的搜尋用 query 當 key，使用者每打一個字，上一次還在 delay(500) 的協程就被取消 —— 不用額外寫任何程式就得到 debounce。對應到 View 系統，大約是 lifecycleScope.launch 加上自己管理 Job 的取消。

rememberUpdatedState：如果 effect 執行很久（例如 LaunchedEffect(Unit) { delay(5000); onTimeout() }），又不希望參數改變時重啟，就用 val currentOnTimeout by rememberUpdatedState(onTimeout)，在協程裡呼叫 currentOnTimeout()，永遠拿到最新的 lambda。

rememberCoroutineScope：由事件啟動的協程

說明

LaunchedEffect 由「進入組合」或「key 改變」觸發；但很多工作是由使用者事件觸發的，例如點擊按鈕。onClick 不是 Composable，也不是 suspend 函式，這時要用 rememberCoroutineScope() 取得一個 scope，再 scope.launch { }。這個 scope 綁定在 Composable 上，離開畫面時所有協程一起被取消，不會洩漏。

取消是協作式的：job.cancel() 只是發出取消請求，協程要執行到取消點（delay、yield、其他 suspend 函式）時才會丟出 CancellationException 結束。單純的清理工作放在 finally 即可；如果需要捕捉它（例如更新畫面上的狀態文字），處理完一定要重新丟出，否則取消會被當成一般錯誤吞掉，後面的程式也會繼續執行。

async / await：平行執行

說明

協程裡的 suspend 呼叫預設是依序執行的，寫起來像同步程式碼，但兩個互不相依的請求就會白白多等。用 async 同時啟動它們，再用 await() 取結果，總時間就是最慢的那一個。

這兩個 async 是外層 launch 的子協程，這就是結構化並行（structured concurrency）：任一個失敗，其他的會一起被取消；外層被取消，子協程也不會被遺留在背景。

切換執行緒：這個網站跑在單執行緒的 WebAssembly 上，所以範例只用 delay 模擬耗時。在 Android 上，阻塞式的 I/O（檔案、舊版 SDK）要包在 withContext(Dispatchers.IO) { } 裡；Retrofit、Room 的 suspend 函式已經自己處理好執行緒，可以直接在主執行緒呼叫。

produceState：把非同步結果變成 State

說明

畫面最常見的非同步需求，是「載入一筆資料，顯示 Loading / 成功 / 失敗」。produceState 把一段 suspend 程式轉成 State：在 lambda 裡對 value 賦值，畫面就會更新。它其實就是 remember { mutableStateOf() } 加上 LaunchedEffect 的組合，同樣支援 key —— 這裡把 attempt 當 key，按 Retry 就會重新載入。

用 sealed interface 描述 UI 狀態，搭配 when，編譯器會檢查每一種狀態都有處理到。另外注意 catch (e: Exception) 前面先單獨處理 CancellationException：取消不是錯誤，不該顯示成錯誤畫面。

Flow 與 collectAsState

說明

suspend 函式回傳一個值，Flow 則是一連串的值，適合感測器、資料庫查詢結果、WebSocket 這類會持續更新的資料。collectAsState(initial) 會在背後收集 Flow，把最新的值包成 State。

用 flow { } 建立的是冷流（cold flow）：有人收集時才開始執行，停止收集就停止。下面關掉開關時，TemperatureChart 離開組合，collectAsState 自動停止收集，Flow 也跟著停下；重新打開時，Flow 從頭開始。runningFold 則把每個新讀數累積成「最近 20 筆」的清單。

在 Android 上：畫面狀態通常放在 ViewModel 裡、在 viewModelScope 中產生，以 StateFlow 暴露，Composable 用 collectAsStateWithLifecycle() 收集。它和 collectAsState 的差別是 App 退到背景時會暫停收集，相當於 repeatOnLifecycle(STARTED)，可以省電也避免在背景更新 UI。

snapshotFlow：把 State 變成 Flow

說明

反過來，有時要對 Compose 的 State 套用 Flow 的運算子，例如「停止拖動後才儲存」、「捲動位置變化時記錄」。snapshotFlow { } 會在區塊中讀到的 State 改變、且區塊的計算結果和上一次不同時發出新值（已內建去重，不需要再加 distinctUntilChanged），接著就能使用 debounce、filter、map 等運算子。

拖動滑桿時 onValueChange 每秒觸發數十次，經過 debounce(600) 後只在停手後存一次。drop(1) 用來略過一開始收集時就會發出的初始值。

把 Callback API 轉成 Coroutine

說明

很多 SDK 只提供 callback 或 listener（定位、藍牙、相機、舊版網路函式庫）。與其在 Compose 裡直接處理 callback，不如先把它們包成 Coroutine，之後就能用前面所有的工具：

  • suspendCancellableCoroutine：一次性的 callback → suspend 函式。結果回來時呼叫 cont.resume(...)，失敗時 resumeWithException(...)；invokeOnCancellation 讓協程被取消時，一併取消底層的 SDK 請求。
  • callbackFlow：持續性的 listener → Flow。每次 callback 用 trySend 發出；最後的 awaitClose { } 會在停止收集時執行，在這裡移除 listener，就不可能忘記取消註冊。

範例中的 LocationClient 是一個假的 SDK。打開 Keep tracking 時 listener 數變成 1，關掉時 awaitClose 執行，listener 數回到 0。

LiveData / RxJava 互通：DisposableEffect

說明

既有專案的 ViewModel 若暴露 LiveData 或 RxJava 的 Observable，不用改寫，加上對應的 artifact 就能直接轉成 State：

Android 專案中的寫法（本頁不執行）
// androidx.compose.runtime:runtime-livedata
val user by viewModel.user.observeAsState()

// androidx.compose.runtime:runtime-rxjava3
val items by viewModel.items.subscribeAsState(initial = emptyList())

它們的原理都是 DisposableEffect：進入組合時訂閱，離開組合時在 onDispose 取消訂閱。凡是「註冊 / 取消註冊」成對出現的 API（listener、BroadcastReceiver、LifecycleObserver），都適合用它。

網頁無法執行 LiveData 和 RxJava，所以範例自己做了一個極簡的 MiniLiveData 與 observeAsState，原理和官方實作相同；官方版本另外綁定 LifecycleOwner，在畫面低於 STARTED 時不會收到更新，回傳型別也是可為 null 的 State<T?>。按 Hide 讓 ScoreBadge 離開組合，observer 數會變成 0；這時繼續加分，再按 Show，會立刻收到最新的分數。

onDispose 是 DisposableEffect 的必要結尾，沒寫會編譯失敗 —— 這是刻意的設計，強迫你想清楚怎麼清理。如果真的沒有東西要清理，通常代表你需要的是 LaunchedEffect 或 SideEffect。
