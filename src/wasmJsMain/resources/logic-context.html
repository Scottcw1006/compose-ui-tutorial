KCoroutine 邏輯層實戰

第 4 章 · 協程基礎

CoroutineContext 與 Dispatcher

每個協程都帶著一包設定：它屬於哪個 Job、在哪條執行緒上跑、叫什麼名字、例外交給誰。這包設定就是 CoroutineContext，其中決定執行緒的 Dispatcher 是 Android 開發最常碰到的部分。

CoroutineContext：協程帶著走的設定

說明

CoroutineContext 像是一個以「型別」為 key 的 Map，常見的元素有 Job、CoroutineDispatcher、CoroutineName、CoroutineExceptionHandler。規則只有三條：

  • 用 + 組合，右邊的元素會蓋掉左邊同類的元素：Dispatchers.Default + CoroutineName("sync")。
  • 子協程繼承父協程的 context，只有 Job 例外：它會拿到一個新的 Job，並掛在父 Job 底下，這就是第 2 章那棵樹的由來。
  • withContext(…) 在區塊內換掉部分元素，區塊結束就換回原本的 context，並回傳區塊的結果。

CoroutineName 的實際用途：在 JVM 上開啟 debug 模式（-Dkotlinx.coroutines.debug）時，執行緒名稱會附上協程名稱，例如 DefaultDispatcher-worker-1 @sync#3，排查問題時很好用。

Dispatcher 與 main-safety

說明

Dispatcher 決定協程在哪條執行緒上恢復執行。Android 上常用三個：

Dispatcher執行緒用途
Dispatchers.Main主執行緒更新 UI 狀態。viewModelScope 預設用 Main.immediate：已在主執行緒時不重新排隊，直接執行。
Dispatchers.IO可以很多條（預設上限 64）會阻塞的 I/O：檔案、java.net、同步版的 SDK。
Dispatchers.Default與 CPU 核心數相同吃 CPU 的運算：排序大量資料、解析 JSON、處理圖片。

Android 官方的慣例是 main-safe：每個 suspend 函式都要能在主執行緒上直接呼叫。換句話說，做阻塞工作的那個函式自己負責 withContext，呼叫端不必、也不應該替它切換。Retrofit 與 Room 的 suspend 函式本身已經是 main-safe，直接呼叫即可。

Android 專案中的寫法（本頁不執行）
class PhotoRepository(
    private val api: PhotoApi, // Retrofit
    private val dao: PhotoDao, // Room
    // 用參數注入，測試時才能換成測試用的 dispatcher（第 7 章）
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO,
    private val defaultDispatcher: CoroutineDispatcher = Dispatchers.Default,
) {
    suspend fun sync() {
        val remote = api.fetchPhotos() // 已經 main-safe，不需要 withContext
        val resized = withContext(defaultDispatcher) {
            remote.map { it.resize(maxWidth = 1080) } // 吃 CPU → Default
        }
        dao.insertAll(resized)
    }

    suspend fun exportTo(file: File) = withContext(ioDispatcher) {
        // 阻塞式 I/O → IO；呼叫端在主執行緒直接呼叫 exportTo() 也不會卡住
        file.bufferedWriter().use { out ->
            dao.getAll().forEach { out.appendLine(it.url) }
        }
    }
}

class GalleryViewModel(private val repo: PhotoRepository) : ViewModel() {
    private val _uiState = MutableStateFlow(GalleryUiState())
    val uiState = _uiState.asStateFlow()

    fun onSyncClick() {
        viewModelScope.launch { // 在主執行緒上執行
            _uiState.update { it.copy(syncing = true) }
            try {
                repo.sync() // 直接呼叫，切換執行緒是 repository 的事
            } catch (e: IOException) {
                _uiState.update { it.copy(error = e.message) }
            } finally {
                _uiState.update { it.copy(syncing = false) }
            }
        }
    }
}

為什麼這一節沒有即時範例：瀏覽器只有一條執行緒，Kotlin/Wasm 也沒有 Dispatchers.IO，切換執行緒的效果無法在這裡呈現。上一節的範例之所以能用 Dispatchers.Default，是因為在瀏覽器裡它其實也跑在同一條執行緒上。

限制同時執行的數量：Dispatchers.IO.limitedParallelism(4) 會得到一個最多同時用 4 條執行緒的 view，適合保護一次只能承受少量連線的資源；limitedParallelism(1) 則保證同一時間只有一個協程在執行，是保護共享狀態的另一種做法（見第 6 章）。
