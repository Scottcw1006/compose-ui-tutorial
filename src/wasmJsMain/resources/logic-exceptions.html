KCoroutine 邏輯層實戰

第 3 章 · 協程基礎

例外處理

同步程式碼的例外沿著呼叫堆疊往上丟；協程的例外則沿著 Job 樹往上傳，而且會順手取消兄弟協程。搞懂這條路徑，才知道 try/catch 該放在哪裡。

例外如何沿著 Job 階層傳遞

說明

子協程因為一般例外（不是 CancellationException）失敗時，會依序發生：

  1. 子協程失敗，通知父協程。
  2. 父協程跟著失敗，並取消其他所有子協程。
  3. 例外繼續往上：coroutineScope 會把它重新丟給呼叫端；如果已經到了樹根，就交給 CoroutineExceptionHandler，沒有設定的話，在 Android 上就是 App 閃退。

範例中，價格 API 在 500ms 失敗，正在載入的評論跟著被取消。切到 async 看一個常見的誤解：在 await() 外面包 try/catch，確實抓得到例外，但 async 失敗的當下就已經通知父協程了，評論一樣被取消，呼叫端一樣收到例外。

try/catch 放哪裡：不希望失敗影響別人，就在會失敗的那個協程裡面處理，例如 async { try { api.price() } catch (e: IOException) { null } }；或者改用下一節的 supervisorScope。包在 launch { } 外面的 try/catch 則完全沒用：launch 立刻返回，例外是之後在另一個協程裡發生的。

supervisorScope 與 CoroutineExceptionHandler

說明

supervisorScope（以及 SupervisorJob）改變了第 2 步：子協程失敗不會讓父協程失敗，也不會取消兄弟。代價是每個子協程要自己負責自己的例外：

  • launch 的例外沒人接手，會交給 CoroutineExceptionHandler。
  • async 的例外會保留在 Deferred 裡，等你 await() 時才丟出。

範例同時下載三張圖，b.png 在 500ms 失敗：

  • coroutineScope：a.png 與 c.png 被取消，例外丟給呼叫端；傳給 launch 的 handler 完全沒有被呼叫，因為例外有父協程接手。
  • supervisorScope：a.png、c.png 照常完成，b.png 的例外交給 handler，呼叫端看到的是正常結束。

適合彼此依賴、缺一不可的工作（同一個畫面的資料）彼此獨立的工作（多個下載、多個事件處理）
Android 例子在 suspend 函式裡平行載入viewModelScope、lifecycleScope

viewModelScope 也會閃退：它底層是 SupervisorJob，一個 launch 失敗不會取消其他工作，但沒被處理的例外仍然會一路丟到執行緒的 uncaught exception handler，讓 App 閃退。ViewModel 裡的 launch 要自己 try/catch，把失敗轉成 UI 狀態。

handler 只在兩個地方有效：樹根的協程（例如 scope.launch(handler)），或 supervisor 的直接子協程。裝在一般子協程上會被忽略，就像範例的 coroutineScope 選項。
