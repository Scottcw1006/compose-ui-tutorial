第 6 章 · 資料流與協作

Channel 與 Mutex

多個協程一起工作時，有兩件事要處理：怎麼把資料從一個協程交給另一個，以及怎麼避免它們同時改寫同一份狀態。對應到 Java 的工具，大概是 BlockingQueue 與 synchronized，只是協程版本用「暫停」取代「阻塞」。

Channel：協程之間的佇列

說明

Channel 就是可以暫停的 BlockingQueue：send 在佇列滿時暫停，receive 在佇列空時暫停。和 Flow 最大的差別是：每個元素只會被一個接收者取走。多個 worker 從同一個 Channel 取工作，就是天然的負載分配（fan-out）。

容量決定了生產端什麼時候要等：

  • RENDEZVOUS（0，預設）：沒有緩衝，send 要等到有人 receive 才返回，雙方「碰面」交接。
  • 指定數字、BUFFERED（64）、UNLIMITED：先放進緩衝區，滿了才等。
  • CONFLATED：只保留最新一筆，send 永遠不用等。

範例的生產端送出 6 筆訂單，兩個 worker 各花 600ms 包裝一筆。沒有緩衝時，生產端每次都要等 worker 有空；容量 4 時，它一口氣送完、提早 close() 去做別的事，worker 再慢慢消化。

大多數時候用 Flow 就好：單純的資料串流用 Flow，它是冷的、會自動清理。Channel 適合「協程之間交接工作」的場景，例如工作佇列、把 callback 事件交給處理迴圈。用 produce { } 建構器建立的 Channel 會在協程結束時自動關閉。

Mutex：保護共享的可變狀態

說明

就算只有一條執行緒，協程之間還是會有競爭：只要「讀取」與「寫回」之間有暫停點，暫停的期間其他協程就可能讀到同一個舊值。範例開 100 個協程，每個賣出 1 張票：

  • no lock：100 個協程都讀到 sold = 0，暫停後各自寫回 1，最後只賣出 1 張。
  • Mutex：withLock 讓「讀取到寫回」變成一個整體，最後是 100 張，代價是它們必須排隊，總時間變長。

和 synchronized 的差別：synchronized 會阻塞執行緒，區塊裡也不能呼叫 suspend 函式；Mutex 等鎖時只是暫停。另外 Mutex 不可重入：已經拿著鎖的協程再呼叫一次 withLock 會永遠卡住。

在 Android 的多執行緒環境：即使中間沒有暫停點，兩條執行緒同時執行 count++ 也會出錯。依情況選擇：

  • 狀態放在 MutableStateFlow，用 update { it + 1 }，它是原子操作，ViewModel 最常用。
  • 單一數值用 AtomicInteger 這類原子類別。
  • 把所有修改都限制在同一條執行緒上，例如 Dispatchers.Default.limitedParallelism(1)。
  • 需要在臨界區內暫停時，才用 Mutex。
