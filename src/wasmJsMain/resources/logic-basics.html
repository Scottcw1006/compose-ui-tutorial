KCoroutine 邏輯層實戰

第 1 章 · 協程基礎

suspend 與協程建構器

協程最常被形容成「輕量的執行緒」，但更準確的說法是：可以暫停、之後再從原處繼續的函式。這一章先看「暫停」到底是什麼，再看啟動協程的三個建構器。

suspend：暫停而不阻塞

說明

suspend 函式可以在暫停點（呼叫另一個 suspend 函式的地方，例如 delay）停下來，把執行緒還回去；等條件滿足後，再從停下來的地方繼續。編譯器會把它改寫成一個狀態機，並多傳一個 Continuation 參數，概念上就是「幫你寫好的 callback」。

對照你熟悉的 Thread.sleep()：sleep 期間執行緒什麼都不能做；在主執行緒上，這就是卡頓與 ANR。範例讓 A、B 兩個協程在同一條執行緒上各做三步：

  • suspend：A、B 交錯執行，總共約 900ms（和只跑一個一樣久）。delay 的 300ms 裡，執行緒去跑另一個協程了。
  • blocking：A 做完三步 B 才開始，總共約 1800ms，而且這段期間整個頁面都卡住，連 Run 按鈕都按不動。

suspend 不會自動換執行緒：在 suspend 函式裡呼叫阻塞式的程式（檔案 I/O、舊版 SDK 的同步 API），一樣會卡住當下的執行緒。要把它移到別的執行緒，得自己用 withContext(Dispatchers.IO)，見第 4 章。

launch、async 與 coroutineScope

說明

suspend 函式只能從另一個 suspend 函式或協程裡呼叫，而協程要由建構器啟動：

建構器回傳用途
launchJob不需要結果的工作：寫入、送出、更新狀態。
asyncDeferred<T>需要結果的工作，之後用 await() 取值；多個 async 會同時進行。
coroutineScope區塊的結果本身是 suspend 函式：在裡面開子協程，等全部結束才返回，任一個失敗就整組取消。
runBlocking區塊的結果阻塞當下的執行緒直到完成，只用在 main() 或舊式測試；Android 主執行緒上絕對不要用，瀏覽器上也不存在。

範例的 loadDashboard 同時抓 user（600ms）與 feed（900ms），另外 launch 一個送出統計的工作（1200ms）。注意看兩個時間點：

  • [dashboard] ready 出現在約 900ms：兩個 await() 都拿到結果了。
  • [caller] returned 卻出現在約 1200ms：coroutineScope 會等「所有」子協程結束，包括沒人 await 的 analytics。

這正是結構化並行的保證：函式返回時，它啟動的工作一定都結束了，不會在背景偷偷繼續跑。如果真的需要「呼叫端不等、而且比畫面活得更久」的工作，就把它 launch 在一個生命週期更長、由你明確注入的 scope（例如 application scope）裡，而不是用 GlobalScope。
