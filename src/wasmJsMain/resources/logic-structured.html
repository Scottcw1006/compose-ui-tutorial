KCoroutine 邏輯層實戰

第 2 章 · 協程基礎

結構化並行與取消

用 Thread 或 Executor 開出去的工作，誰負責停掉它、什麼時候停，全靠你記得。協程把每個工作放進一棵 Job 樹裡：生命週期跟著父節點走，取消也沿著樹往下傳。

Job 階層：父子關係

說明

每個協程都有一個 Job。在協程裡再 launch，新的協程就是它的子協程。這棵樹有四條規則：

  • 父等子：父協程自己的程式碼跑完後，還要等所有子協程結束才算完成。
  • 取消往下傳：取消父協程，它底下的所有子孫都會被取消。
  • 取消不往上傳：子協程被取消（CancellationException）是正常結束的一種，不影響父協程與兄弟。
  • 失敗往上傳：子協程因為其他例外而失敗，會讓父協程也失敗，詳見第 3 章。

Android 上的 viewModelScope 就是一棵樹的根：onCleared() 時它被取消，從它開出去的所有工作一起停止，這就是不會洩漏的原因。

取消是合作式的

說明

job.cancel() 只是把 Job 標記為「已取消」。協程要執行到取消點才會真的停下來，也就是在那裡丟出 CancellationException。kotlinx.coroutines 裡的 suspend 函式（delay、withContext、await、Channel 的收送）都是取消點；一段完全不暫停的 CPU 運算則不是。

範例的 worker 分 8 塊做運算，每塊約 150ms，caller 在 400ms 時取消它：

  • no check：worker 一路跑完 8 塊。更慘的是，在單執行緒的瀏覽器裡，caller 的 delay(400) 要等 worker 讓出執行緒才能結束，所以 cancel() 晚到 1200ms 才被呼叫，這時已經沒東西可取消了。在 Android 的 Dispatchers.Default 上，cancel() 會準時在 400ms 呼叫，但結果一樣：迴圈照跑到底。
  • yield()：每一塊開始前先 yield()，讓出執行緒、也檢查是否被取消。caller 因此很快就能呼叫 cancel()，worker 在下一個 yield() 停下，剩下的幾塊都不做了，finally 照常執行。

三種讓 CPU 迴圈可以被取消的寫法：

  • yield()：檢查取消，並讓同一條執行緒上的其他協程有機會執行。單執行緒（主執行緒、瀏覽器）上要用這個。
  • ensureActive()：只檢查、被取消就丟例外，不讓出執行緒，比較便宜。在 Dispatchers.Default 這種多執行緒環境足夠了。
  • while (isActive) { … }：不丟例外，迴圈自然結束，適合需要自己收尾的情況。

別把取消吞掉：catch (e: Exception) 與 runCatching { } 都會抓到 CancellationException。抓到後沒有重新丟出，協程就會「忘記」自己被取消，繼續往下執行。要嘛只抓具體的例外型別，要嘛先 if (e is CancellationException) throw e。

finally 裡的 suspend 呼叫：已取消的協程再呼叫 suspend 函式會立刻丟出 CancellationException。如果收尾一定要暫停（例如把進度寫進資料庫），包在 withContext(NonCancellable) { } 裡。

逾時也是取消：withTimeout(3000) { } 超時會取消區塊並丟出 TimeoutCancellationException；withTimeoutOrNull 則回傳 null，通常比較好處理。兩者一樣需要區塊內的程式碼配合取消。
