State 與重組

View 系統是「命令式」的：資料變了，你要自己呼叫 textView.setText() 去改畫面。Compose 是「宣告式」的：你描述「資料長這樣時，畫面長這樣」，資料一變，Compose 會自動重新執行相關的函式 —— 這個過程叫做重組（Recomposition）。

remember 與 mutableStateOf

說明

要讓畫面隨資料更新，需要兩樣東西：

  • mutableStateOf(...)：一個「可被觀察」的值。讀取它的 Composable 會被 Compose 記下來，值改變時就會重組。
  • remember { ... }：Composable 函式每次重組都會重新執行，remember 讓值在重組之間保留下來，否則每次都會被重設成初始值。

by 是 Kotlin 的屬性委派，讓你直接讀寫 count 而不用寫 count.value。數字型別建議用 mutableIntStateOf，可以避免裝箱（boxing）。

remember 只在重組之間保留值。在 Android 上遇到旋轉螢幕等 configuration change 時，要改用 rememberSaveable，或把狀態放進 ViewModel。

輸入框：單一資料來源

說明

TextField 本身不保存文字。它只顯示你給的 value，使用者輸入時透過 onValueChange 通知你，由你決定要不要更新狀態。

這和 EditText 自己管理內容、你再用 TextWatcher 監聽的方式完全相反。好處是狀態永遠只有一份，輸入框、下方的問候語、字數統計都讀同一個變數，不可能不同步。

狀態提升（State Hoisting）

說明

當多個元件需要共用同一份狀態時，把狀態「提升」到它們共同的父層，子元件只接收兩樣東西：

  • value：目前要顯示的值
  • onValueChange：要求改變的事件

這樣的子元件稱為無狀態（stateless）元件，好處是容易重複使用、容易測試、也容易在 Preview 中預覽。下面的 Stepper 不知道自己是在數蘋果還是橘子，總數則由父層計算。

原則：狀態往下傳，事件往上丟（state flows down, events flow up）。實務上，畫面層級的狀態通常會一路提升到 ViewModel，以 StateFlow 暴露，再在 Composable 中用 collectAsStateWithLifecycle() 收集。
